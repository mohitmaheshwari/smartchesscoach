Before declaring work done, verify end-to-end that the delivered output matches the vision the user described. Do not hand over drafts with the structure correct but the content sparse.

**Why:** The user has repeatedly caught me shipping work that technically "does the thing" but doesn't match what they asked for in substance — a /today screen with the layout right but the evidence/board/streak empty; a home page with the voice right but fortune-cookie short. Every time I shipped and said "try it", they opened it and found gaps that should have been caught before declaring done. That wastes their time and erodes trust. They've now asked explicitly: "make this a rule — don't deliver anything until the vision matches."

**How to apply:**
- Before saying "done" or "try it", re-read the vision statement the user gave (headline + evidence + board + rule + streak + action; coach voice; concierge not catalog; etc.) and verify every element is actually present in the output I'm about to hand over.
- Run the output through the user's actual data (their rating, their games, their focus) to confirm — don't trust that "if data exists it'll show up."
- If any vision-critical element is silent or falling back to empty (evidence list empty, board null, streak null, CTA falling through to generic fallback), FIX IT FIRST. Don't ship with gaps and wait to be told.
- When a data pipeline has fallbacks, make sure the fallbacks actually produce something rather than quietly returning nothing.
- If the vision cannot fully be met due to missing data/content, say so *explicitly up front* — don't ship a reduced version hoping the user won't notice.
- The user's standard is: the screen they open should feel like the vision, not "the skeleton of the vision." Don't settle for skeleton.
