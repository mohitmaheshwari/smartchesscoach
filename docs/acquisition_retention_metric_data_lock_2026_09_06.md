# Acquisition Retention Metric — Data Lock

**Status:** LOCKED

**Date:** 2026-09-06

**Input:** `backend/data/corpus_snapshots/acquisition_retention_baseline_2026-09-06.json`

**Existing authority:** `docs/product_analytics_source_map.md`

## Decision

Which current metric may define ChessGuru's retention baseline and numerical improvement target?

## Candidates measured

| Candidate | Measured result | Discriminating defect |
|---|---|---|
| A. `users.last_login` | Six accounts in the preceding 30 days; five excluding admins | The field exists for only 38 of 125 accounts. It exactly reproduces the alarming “six users” headline but is not a complete activity record. |
| B. `user_sessions.created_at` on a later UTC date | 14 of 124 accounts returned; 110 did not. Non-admin: 13 of 121 returned | Session tokens are long lived. A returning browser can reuse a cookie without creating a new record, so absence is not proof of absence. |
| C. Union of existing Mongo activity timestamps | 32 recent accounts; 31 excluding admins | Some lesson/journey/session timestamps can be generated by validation, migration or administrative activity, and records lack one uniform actor/environment provenance field. |
| D. Existing canonical PostHog interaction events | Not measurable from the repository; no authenticated export for a clean window | The repository correctly assigns interaction measurement to PostHog, but the available window is pre-launch/contaminated and current production counts are not versioned. |

## Decision locked

**VALUE: No current candidate is authorized to set a numerical retention target.**

The future primary interaction metric will extend the existing PostHog event registry rather than create a second analytics system:

> Among newly eligible non-internal users, the proportion with at least one allowlisted authenticated player-action event on a later UTC date after first value, reported separately for D1 and D7.

Mongo remains authoritative for coaching completion and learning/transfer. `complete_coaching_journeys` proves journey steps; it does not synthesize a “returned” event. PostHog interaction and Mongo outcome are reported side by side, never substituted for one another.

## Evidence

- `last_login` coverage is 38/125, so its six-user count cannot represent complete product activity.
- Later-day auth session creation reports 14/124, while the measured union of direct-action sources reports 32 recent users. The difference is too large to treat either shortcut as interchangeable retention truth.
- The existing analytics source map already declares PostHog the product-interaction owner and Mongo the product/learning-state owner.
- The existing server snapshot explicitly says the 2026-08-28 funnel is structural reach, not an engagement baseline.
- Play-with-Coach early exit is independently measurable in Mongo (134/294 mature non-admin sessions under two player moves), demonstrating why retention and journey quality need separate metrics.

## Rejected candidates

- **A — `last_login`:** rejected for 30.4% field coverage.
- **B — auth-session creation:** rejected because token reuse makes it an event about authentication issuance, not return behavior.
- **C — Mongo union:** rejected until actor/environment provenance separates customer actions from tests, migrations and administrative work.
- **D — historical PostHog window:** rejected for target calibration because no clean, versioned, authenticated baseline exists.

## Measurement method

Read-only production aggregation through the backend container's environment. No identities, credentials, games, positions or production writes were exported. The anonymized inputs and all compared definitions are frozen in the linked JSON snapshot.

## What unlocks the number

1. Verify one staging journey from each allowlisted event emitter through PostHog's event inspector.
2. Every event used by the retention metric carries or resolves to an explicit customer/internal/test classification and rollout cohort.
3. Freeze a UTC cohort start after deployment; do not use the contaminated pre-launch history.
4. Export D1 and D7 denominators, successes and exclusions for the fresh cohort.
5. Compare at least two candidate thresholds against the observed distribution and product capacity.
6. Lock the target in a second data-lock note before using it as a release or score gate.

Until those steps occur, retention remains a confirmed P0 risk and a numerical-target evidence gap—not zero, six, or 105/119 as an authoritative product KPI.
