## 1. Why this system is unusually hard to test

**The ground truth is chess, not code.** A detector can pass every unit test,
have 100% branch coverage, and still be wrong about the position. Conventional
testing cannot catch that.

So this strategy has a layer most products do not need: **a chess-truth oracle**,
and every claim the coach makes is graded against it.

Second hazard, and it is subtle: **the D_live thresholds were locked from this
corpus.** Measuring the detector on the same corpus is circular — it will look
better than it is. Everything in Layer 2 runs against a **held-out slice the
thresholds never saw.**

---

## 2. The layers

```
L0  Chess-truth fixtures        the oracle everything is graded against
L1  Unit + property-based       the code does what it says
L2  Detector quality            precision AND recall, regression-locked
L3  Pipeline integration        the stages hand off correctly
L4  Synthetic player cohorts    the coach behaves correctly over time  ★
L5  Honesty tests               it never claims what it cannot prove   ★
L6  Voice + continuity          it sounds like one coach
```

L4 and L5 are the ones that decide whether the product is what you pitched.

## L0 · Chess-truth fixtures

A versioned gold set — `backend/tests/gold/piece_safety.json` — where every entry
is independently verified, not asserted:

```json
{
  "id": "ps-014",
  "fen": "8/8/4p3/8/8/8/8/3QK2k w - - 0 1",
  "move": "d1d5",
  "truth": { "hangs": true, "see_cp": 900, "attacker": "e6", "difficulty": "easy" },
  "why": "queen steps onto the e6 pawn's square, no defender",
  "verified_by": ["stockfish", "independent_see", "human"],
  "verified_on": "2026-08-27"
}
```

Rules that make it an oracle rather than a snapshot:
- **Two independent implementations must agree** — production SEE (least-valuable
  attacker) and an exhaustive capture-tree — plus an engine eval. The existing
  `audit_d_live_outcome_validation.py` already does exactly this pairing.
- **A human signs each entry.** Machine eligibility is not human acceptance.
- **Never generated by the detector under test.** That is the circularity trap.
- Entries carry `verified_on`; a stale entry is re-verified, not trusted.

**Coverage the gold set must include** (each is a real failure mode):
easy hangs · defended-but-contested (SEE 0) · compensated sacrifices (SEE high,
`cp_loss` low) · x-ray and discovered attackers · en passant · promotion ·
castling · pinned defenders (a defender that cannot legally recapture) ·
mate-in-1 overriding material · already-lost positions · king moves.

Target: **200 entries**, stratified by rating band and difficulty.

## L1 · Unit and property-based

Conventional unit tests for pure functions — SEE, the d_live predicate, rep
construction, difficulty classification, the state machine.

**Boundary tests are mandatory** where a locked number lives:
`cp_loss` 149 / 150 / 151, SEE 99 / 100 / 149 / 150 / 151. Every threshold gets
tests on both sides; the `[100,150)` rejection band gets its own.

**Property-based tests** are the high-value addition here (`hypothesis`). Over
randomly generated *legal* positions, invariants must hold regardless of input:

| Property | Why it catches real bugs |
|---|---|
| If the generator says `safe`, no opponent capture sequence wins ≥150 | Catches SEE bugs no fixture thought of |
| If it says `not_safe`, such a sequence exists and is legal | Prevents phantom danger |
| Every generated rep's move is legal in its FEN | The exact bug that broke 92% of motif drills |
| `is_safe` boards show the position *before*, others *after* | The board must not contradict the prompt |
| Rep generation is deterministic under a fixed seed | Makes every other test reproducible |
| No rep is ever served from schema < 16 | Pre-SEE residue must never reach a user |

## L2 · Detector quality — precision **and** recall

This is where the product's credibility lives, and where `simple_hang` was caught
out: 96.9% precision, but recall unmeasured for a year and then found to be
61.61% inside its own taxonomy.

**Every detector ships with both numbers or it does not ship.**

| Metric | How | Floor |
|---|---|---|
| Precision | Sample N fires, verify each against L0 | locked per detector |
| Recall | Sample N gold positives, count how many fire | locked per detector |
| Confusion | Full matrix across gap categories | no category >10% cross-contamination |

**Regression locks.** Precision and recall floors live in a committed file; the
test fails if a change drops either. A detector improvement that raises recall
while dropping precision below its floor is a regression, not a win.

**Held-out corpus.** Split by `user_id`, not by move — same-game moves are
correlated and would leak. Thresholds were tuned on the training slice; all L2
numbers are reported on the held-out slice only.

**Run against several datasets, and report separately:**
1. Held-out real corpus (the honest number)
2. Gold set (the strict number)
3. Adversarial set — compensated sacs, mate lines, already-lost positions
4. Rating-band strata — a detector good at 1800 and bad at 800 is bad for you

## L3 · Pipeline integration

Stage-by-stage contracts, with a real (test) database:

- import → analyse → observations: schema 17, `piece_safety.d_live.v1` present
- observations → focus selection: recurrence, not one-off; decay respected
- focus → plan: instruction resolved **once**, immutable thereafter
- game completion → evidence → verdict: correct D_live counts
- **Idempotency**: analysing the same game twice produces identical evidence and
  does not double-count. Assert on the idempotency key.
- **Flag off is a true no-op**: with `PERSONAL_IMPROVEMENT_CYCLE_ENABLED=false`,
  every endpoint behaves exactly as before. Snapshot-compare responses.

## L4 · Synthetic player cohorts ★

**This is how you prove "makes you improve" before touching it manually.**

Generate PGN sets with *known* ground truth, run each through the entire loop,
and assert what the coach does. Each cohort is a claim about the product.

| Cohort | Constructed behaviour | The coach MUST |
|---|---|---|
| **P1 Chronic** | hangs in 60% of games, never improves | never resolve the focus; keep saying "again"; number stalls |
| **P2 Learner** | hangs for 10 games, then stops cleanly | resolve — but **only after 20 clean D_live decisions**, never earlier |
| **P3 Clean** | never hangs a piece | **not** select piece safety as the focus |
| **P4 Sparse** | 3 games total | say "not measured"; never manufacture a diagnosis |
| **P5 No-opportunity** | games with zero D_live decisions | say "that game didn't test it"; number does not move |
| **P6 Regressor** | clean, then relapses | demote `Proven` → `Remembered · Refresh needed` |
| **P7 Sacrificer** | sound sacrifices (SEE high, `cp_loss` low) | **never** flag these as hangs |
| **P8 Wrong-phase** | loses in endgames, decided in middlegame | route to the middlegame, not endgames |

P2 is the single most important test in this document: it asserts the product
**cannot declare success early**. P7 is the adversarial one — it is the case that
made raw SEE unusable.

Cohorts are fixtures, versioned, deterministic, and fast (no engine calls at run
time — pre-computed evals stored alongside).

## L5 · Honesty tests ★

Negative tests that assert the product **does not lie**. These protect the moat
and should be the hardest to delete.

- No `improved` / `fixed` / `resolved` claim exists without the required
  independent evidence — assert across every rendered string in a full run.
- Assisted practice (hints, Guardian intervention, reveals) **never** produces
  `evidence_eligible: true`.
- A revealed or skipped rep never advances a checkpoint.
- Zero-opportunity game → literal `not measured`, never "good job".
- No claim of "fixed" outside `piece_safety` — every other category is
  coaching-only.
- No user-facing string contains an internal state name
  (`checkpoint_insufficient_evidence` and its eight siblings must never render).
- Personal-game copy names a game/date/move only when provenance is exact.
- No date is ever promised for a fix.

---

## L6 · Voice and continuity

- Every rendered coaching string passes `pwc_coaching_lint.py` — no jargon, no
  `snake_case` leak, no "1 mistakes", no pawn called a piece.
- **Continuity test (the pitch's core claim):** in one run, the instruction shown
  in review, on Home, in reps, in PWC and in the verdict is the **same
  `instruction_id` and the same literal text**. Any mismatch fails the build.
- No caption restates the destination square SAN already names.
- Every engine-confirmed mistake caption carries a why.

## 3. What runs when

| Gate | Layers | Budget |
|---|---|---|
| Pre-commit | L1 fast subset + voice lint on changed files | < 10s |
| Every PR | L1, L3, L5, L6, plus L2 on the gold set | < 5 min |
| Nightly | Full L2 on held-out corpus + all L4 cohorts | ~30 min |
| Before any rollout | Everything, plus the regression-lock report | — |

**A detector change cannot merge without its nightly L2 numbers attached.**

## 4. Determinism, or none of this is real

- Every random path takes an explicit seed. `$sample` in MongoDB is **not**
  seeded — never use it in a test; use a fixed id list.
- No engine calls inside tests; evals are pre-computed into fixtures.
- No wall-clock dependence — inject the clock.
- Any test that fails intermittently is deleted or fixed the same day. A flaky
  suite trains people to ignore red, which is how 3,098 tests became 4.

---

## 5. Coverage — and its limits

Track line and branch coverage on the detector, rep-generation, focus-lifecycle
and evidence modules; floor at **85%**, and no uncovered branch in the d_live
predicate or the state machine.

But state plainly: **coverage measures which lines ran, not whether the chess was
right.** A 100%-covered wrong detector is still wrong. L0/L2/L4 are what actually
protect this product; coverage is a hygiene metric that stops obvious rot.

Worth one run of **mutation testing** (`mutmut`) on the d_live predicate
specifically — if flipping `>=` to `>` there does not fail a test, the boundary
tests are inadequate.

## 6. Build order

1. **Task 0** — make the 3,098 existing tests run in CI. Nothing else counts
   until this is done.
2. **L0 gold set**, 200 entries, human-signed.
3. **L2 harness** with held-out split + regression locks; publish current
   precision/recall for every live detector, including the ones nobody has
   measured.
4. **L5 honesty tests** — cheap, and they guard the differentiator.
5. **L4 cohorts** P1–P8. This is the "prove it improves people" deliverable.
6. **L1 property tests** as detectors are touched.
7. **L3 + L6** alongside the Tier 0 wiring work.
8. Coverage floors and the mutation run last, as hygiene.

## 7. Alignment risks I would flag before you test manually

Being direct, since you asked me to be sure:

1. **Two rep paths still coexist** — the PIC `best_move_san` lesson and the
   `is_safe` scan generator. Until L4 runs against one of them, "the plan" is
   ambiguous. **Resolve before testing manually**, or you will be testing two
   products.
2. **D_live proves piece safety only.** The pitch promises broad coaching. Every
   other category is currently coaching-only and cannot be part of an improvement
   claim. The honesty register must hold.
3. **PIC's nine internal states have no translation layer yet.** If one leaks
   into the UI during your manual test, that is a missing layer, not a bug in
   the state machine.
4. **Codex is building UI against a spec that is still moving.** Freeze the
   payload contract — eligibility, focus label, instruction id + text, learner
   state, evidence counts, one typed next action — before that work goes deep,
   or the two halves will not meet.
